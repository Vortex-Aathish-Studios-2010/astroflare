1. Architecture

Three programs in one container; only the interface is public.

Design decisions

  • Engine in Python, standard library only. No third-party packages: nothing to install, no supply chain to audit, and the whole engine runs from a single command.
  • Interface as a thin Node server. It serves one self-contained page (one inline script, pinned by hash in the CSP) and relays a fixed list of API routes to the engine. The same handler also runs as a Cloudflare Worker, which is how the original public deployment works.
  • AI behind the engine. The browser never talks to an AI service. The engine builds each prompt from validated data, calls the router and validates the reply, so keys and prompts never reach a client.
  • Everything stateless. The server stores no mission data and writes nothing durable. FreeLLMAPI keeps a SQLite file, which is deliberately empty on each start because the free plan keeps no files; its keys are re-seeded from a secret each time.
  • One public port. The router (3001) and the engine (8001) listen on 127.0.0.1 only. Render assigns the public port to the interface.

Request lifecycle: a mission assessment

  1. The browser posts answers to /api/assess on the interface (size-capped at 262,144 bytes).
  2. The relay checks route and method against an allow-list, forwards the body and the visitor address (X-Forwarded-For) to http://127.0.0.1:8001, and drops cookies and authorisation headers.
  3. The engine checks host and origin, parses and validates every field against the schema (units, ranges, options), and runs the deterministic assessment.
  4. The result returns through the relay with no-store caching. No AI is involved at this point.
  5. Only if the user presses an AI-backed control does the engine build a prompt, apply the rate limits, call FreeLLMAPI, validate the reply, and return it labelled or withheld.

No ignition-limit comparison. Let-through energy is shown but never compared with an ignition threshold, because the project holds none. This is stated wherever the value appears.

The heuristic index

A sum of developer-chosen points over the factors that apply to the hazard (gravity, mission phase, ventilation and, for battery and isolation hazards, extra terms). It is computed only when every needed input was supplied, labelled uncalibrated and unvalidated, comparable only within the same hazard, and has no tiers and no 0-100 scale. An earlier score with silent defaults was removed.

Basis rules

A weak basis (estimate, assumption) is listed in the limitations. A provision claimed at its strongest level ("verified", "tested") with only an estimate behind it is flagged as unverified; one with no stated basis is flagged as unchecked. The basis never changes a calculation or a rule.

Sensitivity

"Which answer matters most" re-runs the assessment with each select-type answer changed in turn (about 150 runs) and reports how far the index moves and which findings appear or disappear. Numeric answers are not varied because no defensible range exists. Limited to 12 runs per visitor per minute in production.

4. Evidence data and the explorer

Literature library

engine/evidence/sources.json (library version 2026-10-21): 14 sources, 37 statements, plus "tensions" notes where cited statements concern different conditions and cannot be combined. Each statement has an id such as S04.c2; findings cite those ids. Verification checks each record live at NTRS for existence and matching title (rate-limited to one real check per 30 seconds); it does not re-read content.

PSI data set

public/dataset.json holds three investigations and eight curated runs, each with the original raw row, units, conditions, outcome fields and a source link. Every original CSV under sources/ is pinned by SHA-256, and test/source-audit.py re-checks curated values against the pinned bytes. Unreported fields are shown as "Not reported" and a number is never inferred.

Ranking algorithm (public/research.js)

RulePoints
Each recognised question topic (solid materials, flame spread, ventilation, oxygen, microgravity, combustion gases); repeats count once+2
Variable-flow investigation when airflow is asked about+1
Specific material named in the question or filter and supported+2
Exact scenario-gravity match (a mismatch is disclosed, no point)+1
Tiesfixed order: BASS-II, Saffire II, Saffire I

Evidence answers

  • A named investigation and a requested measurement are resolved before ranking: "Saffire II", "Saffire 2" and "PSI-99" all map to PSI-99 only.
  • Flame-spread rate, burn time, airflow, oxygen and carbon monoxide are separate quantities; a question naming more than one is asked to be narrowed.
  • Requests for safe limits, predictions, certification or numeric extrapolation return a gap message. Lunar-gravity flame spread returns the explicit statement that no lunar measurement exists.
  • Each answer ends with the NASA table link, file name and row id. A latest-request-wins coordinator discards late responses when the user changes the question or filters.

Calls and fallback

The engine sends an OpenAI-style chat request to the router. For each model in the configured list (up to five), a model that fails for a provider-side reason (retired, rate-limited or cooling down, slow, bad response, truncated) is skipped and the next is tried, inside a 70-second total budget; a model that stays silent is abandoned after 30 seconds while others remain. Failures that no other model can fix (such as an invalid key) stop immediately. Errors are reduced to generic public messages; provider names, models, keys and stack traces appear only in developer mode, which production ignores.

Router start-up on Render

  1. render_start.py starts FreeLLMAPI on 127.0.0.1:3001 with an encryption key (random if unset) and a database path in the container.
  2. FreeLLMAPI applies FREEAPI_CONFIG_JSON on boot, loading the provider keys.
  3. When the router answers, the script reads the router's freshly generated access key from its settings table (read-only) and starts the engine with it. The key is never printed and never given to the interface.
  4. The engine starts on 127.0.0.1:8001; when its health check passes the interface starts on the public port.
  5. If the router fails to start, the site still runs without AI. Router and engine are restarted up to five times if they crash.

Error behaviour

400 invalid input (the message names the field); 404 unknown route; 405 wrong method; 413 oversized body; 415 non-JSON content type; 429 per-visitor limit; 502 engine unavailable (relay). AI failures are not HTTP errors: they return 200 with a mode of unavailable or withheld and a plain message.

Found and fixed during testing. The Node interface initially sent only two security headers. The content-security policy, frame, permissions and HSTS headers that the earlier Python site sent were missing. The build now hashes the page's single inline script and the server sends a strict policy that allows only that script; tests assert the hash matches. See the test report.

Secrets

  • Provider keys live only in the Render secret FREEAPI_CONFIG_JSON. They are never in the repository, the image (.dockerignore excludes .env) or logs.
  • The router's access key is generated at each start and handed only to the engine. Error text from services is stripped of key-like strings before use.
  • Developer-only routes and diagnostics are disabled in production regardless of settings.

Free-plan behaviour

  • The service sleeps after about 15 minutes without traffic; the next visit takes about a minute while all three programs start, and the router re-loads its keys.
  • Memory is 512 MB for everything: the router's Node heap is capped at 256 MB and the interface's at 96 MB.
  • Auto-deploy is off. A change goes live after Manual Deploy, Deploy latest commit; a failed build leaves the previous version serving.
  • FreeLLMAPI's usage statistics and any dashboard changes reset on every start; its keys and the generated access key are re-created automatically.
